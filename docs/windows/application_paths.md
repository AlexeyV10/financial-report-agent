# WIN-04 · Явные пути Windows и рабочее хранилище

`ApplicationPaths` принимает два абсолютных пути при запуске. Корень установки
служит источником кода и ресурсов. Пользовательские данные, кеш, модели и журналы
получают отдельный корень. `WorkspaceContext.open` принимает третий абсолютный
путь к выбранному vault. Все три корня разделены. Класс проверяет существующие
компоненты путей и отклоняет символьные ссылки и reparse points. Путь текущей
папки процесса и расположение репозитория не участвуют в выборе корней.
[Модуль](../../src/financial_assistant/application_paths.py).

В `workspace.json` закреплены версия `workspace-context-1`, ID хранилища и реестр.
Запись ресурса содержит логический ID, относительный путь, размер в байтах и
SHA-256. Логические ID уникальны без учёта регистра. Путь ресурса не принимает
абсолютные ссылки, `..`, ADS и имена устройств Windows. Проверяются тип файла,
размер и хеш фактически прочитанных байтов. Следующие этапы сохраняют эти ошибки
в типизированном ответе.

| Ситуация | Код |
| --- | --- |
| Нет файла с таким путём | `source_missing` |
| Изменился размер файла | `source_size_mismatch` |
| Байты отличаются при том же размере | `source_hash_mismatch` |
| Нет такого логического ID в реестре | `resource_not_registered` |
| Компонент пути — ссылка или reparse point | `path_escape` |
| Квитанция с таким ID уже сохранена в vault | `duplicate_run` |

`resolve_legacy_resource` проверяет ресурс из старого `ROOT/tmp`, если вызывающий
код явно передал реальный корень, точный дескриптор и логический ID. Прежние
контексты и индексы остаются на своих версиях. Перед записью квитанции формируется
полный JSON. Windows публикует его переименованием внутри того же каталога с
отказом при уже существующем имени. Результаты лежат в `runs/` выбранного vault.

## Сквозное испытание

Временная установка собрана из проверенного stock runtime WIN-03, существующего
калькулятора и отдельной точки входа WIN-04. Установочные файлы получили атрибут
только чтение. Проверка записи в существующий файл была отклонена, а итоговая
инвентаризация показала прежние хеши всех 266 файлов. PDF лежал в двух разных vault.

Из третьей, пустой рабочей папки запущен частный Python. Оба vault с кириллицей
дали `15.00%`, страницу 1 и одинаковую выделенную ячейку. Одинаковый ID задания
был допустим в двух разных хранилищах, повтор в одном хранилище отклонён. Одно
хранилище перенесено целиком, его ID и предыдущий результат прочитались по новому
пути. Сценарии отсутствующего и изменённого PDF сохранили прежнее состояние обоих
хранилищ. Прогон использует только вымышленный отчёт. [Квитанция](../../evaluation/windows_04_2026-11-19/workflow.json).

На MSYS2 Python 3.14.7 и stock CPython 3.14.10 прошли по 10 тестов. В обоих
прогонах подтверждены отказ при выходе через reparse point и единственная запись
квитанции при одновременном обращении. Двоичные контрольные суммы всех 134 файлов
протокола и 329 файлов RC1 совпали с обоими замороженными манифестами.

```powershell
python -X utf8 -I -B spikes/windows_04/check_workflow.py --runtime-build tmp/runtime-a --demo tmp/own-demo --out tmp/workspace-e2e
```

Рецепт runtime и состав комплекта `tmp/own-demo` приведены в [WIN-03](stock_runtime.md).
Сценарий создаёт новый собственный каталог в `tmp/`. Он подтверждает работу
нативного Python-процесса в расположении установки. Подключение GUI и CLI к общему
сервису идёт следующим этапом. Проверка пути и хеша описывает наблюдавшийся файл.
Для защиты от параллельной подмены после проверки нужен закреплённый открытый файл
или отдельный неизменяемый снимок в протоколе хранения. [Сценарий WIN-05](../../prompts/windows_05_typed_service.md).
