# Шаг 7: финансовый инструмент по ID фактов

09.11.2026. Реализован явный вызов `annual_growth_v1` по двум ID и связка поиска с прежним ручным реестром. Арифметика остаётся в **единственном** существующем `contracts.answer(bundle)`. Ни второй формулы, ни нового извлечения/подтверждения чисел не добавлено.

## Что изменилось

Раньше `answer` сам выбирал пару по контексту Request внутри bundle; отдельно запустить инструмент по выбранным ID или безопасно связать его с поисковой выдачей было нельзя. `src/financial_assistant/finance.py` теперь связывает эти границы. Большой рефакторинг не нужен: чистая обёртка переиспользует уже проверенный калькулятор и `validate_answer`, сохраняя строгий Answer v0.1.

`calculate_metric(bundle, request)` — прямой вызов по ID, не требует PDF, сети или индекса. Он проверяет внутреннюю согласованность ранее вручную проверенного реестра, **не выполняет новую сверку первоисточника**. `calculate_from_retrieval(bundle, request, retrieval)` дополнительно требует, чтобы выдача покрывала оба нужных прежних Evidence по точным локаторам. CLI `from-search` вызывает текущий локальный поиск с проверкой исходного PDF и индекса.

## Команды Windows

Из корня проекта:

```powershell
python scripts\calculate_financial.py calculate --previous-fact phosagro-revenue-2023 --current-fact phosagro-revenue-2024
```

Поиск → прежние Evidence/Fact → тот же расчёт:

```powershell
python scripts\calculate_financial.py from-search --previous-fact phosagro-revenue-2023 --current-fact phosagro-revenue-2024 --output output\finance-result.json
```

Для второй команды нужны `tmp/pdfs/phosagro-2024-ru.pdf` и `tmp/retrieval/document.sqlite`, уже созданные на шаге 6. Команда не пересоздаёт индекс и не переключает режим при его отсутствии. Построение описано в `docs/retrieval.md`. Параметры `--db`, `--pdf`, `--query`, `--top-k` позволяют выбрать явные локальные входы; поиск не заменяет реестр.

Реальный результат: **+67 385 млн RUB, +15,30%**, значения 440 304 и 507 689 млн RUB, полные 2023/2024 годы. Доказательства — PDF 4, левая половина, печатная 320, строка выручки, колонки 2023 и 2024, версия с хешем из реестра. Вывод содержит их локаторы и прямые URL. Это изменение выручки по опубликованным суммам, не органический рост, причинный эффект или инвестиционный вывод.

Исторический запрос:

```powershell
python scripts\calculate_financial.py calculate --previous-fact phosagro-revenue-2023 --current-fact phosagro-revenue-2024 --mode historical_as_of --as-of 2025-02-14T10:00:00+03:00
```

Ожидается `missing/publication_unknown` и отсутствие расчёта. То же ограничение действует для `from-search`. Подпись, fetched_at и дата другого ZIP не превращаются в публикацию выбранной PDF-версии.

Если ограничить поиск первым результатом `--top-k 1`, инструмент возвращает `missing/verified_evidence_not_retrieved`: первое примечание не содержит ссылок на оба нужных Evidence. При пяти результатах используется второй фрагмент с целевой таблицей. Нет скрытого перехода к прямому расчёту при неудачном поиске.

## Формат и правила

Вход FinancialToolRequest v0.1:

```json
{
  "operation_id": "annual_growth_v1",
  "previous_fact_id": "phosagro-revenue-2023",
  "current_fact_id": "phosagro-revenue-2024",
  "mode": "document_snapshot",
  "as_of": null
}
```

ID должны быть разными и существовать в реестре. Группа, стандарт, показатель и два полных периода задаются существующим `bundle.request`, а не угадываются из произвольного числа или текста. Входы не сортируются молча: поменянные местами ID дают конфликт. Другой показатель/период по ID не подменяет исходный вопрос. Весь реестр сохраняется при вызове калькулятора: второй кандидат на ту же роль не исчезает из-за передачи удобной пары ID.

`mode/as_of` — явный контекст операции; в историческом режиме нужен корректный timestamp с часовым поясом. Запрос обрабатывается по той же `available_from`-политике, что прежний калькулятор. Нельзя вызвать прямой инструмент и тем самым обойти неизвестную или будущую публикацию.

FinancialToolResult v0.1 — **новый внешний конверт**, не изменение обязательных полей Answer v0.1:

| Поле | Смысл |
|---|---|
| `financial_tool_schema_version`, `request` | Версия и точные переданные аргументы |
| `status`, `reason_code`, `message` | Результат операции/отказа |
| `basis` | `preverified_manual_fact_registry`; происхождение чисел явно ручное |
| `document_id`, `entity_name`, `accounting_standard`, `metric_id`, `requested_periods` | Предмет и интервалы операции |
| `answer` | Прежний валидированный Answer либо null при отказе на границе ID/поиска |
| `inputs`, `sources` | Оба использованных Fact и минимальные локаторы Evidence, только при успешном расчёте |
| `warnings` | Обязательные ограничения, включая происхождение проверки/версию/права |
| `retrieval_resolution` | Ранги/ID использованных фрагментов и доказательств, метод сопоставления, режим извлечения, `new_facts_created=false`; null для прямого вызова |

В `answer.calculation` сохранены формула/версия, упорядоченные ID, абсолютное изменение, валюта/масштаб, внутренний Decimal и отображение, 50 значащих цифр и HALF_UP до двух знаков. Это приближённая десятичная запись, не точность документа до 50 знаков. Источники сохраняют строку/колонку, период, единицу, страницу, регион, версию/хеш, исходное написание и происхождение проверки.

`validate_financial_result(result, bundle, request, retrieval=None)` повторно получает детерминированный результат и сравнивает **весь конверт с внешними аргументами**. Замена расчёта, источников, входов, предупреждений или трассы не проходит проверку. Это защита согласованности, не независимый аудит истинности исходных ячеек; независимая арифметическая проверка остаётся Fraction-тестом.

## Как связывается поиск

Перебираются все hits, а не первый. Для каждого проверяются документ/группа/версия/хеш, диапазон страницы, сторона, fragment_id и URL. Статус должен оставаться `candidate`: попытка повысить его до `human_reviewed` отклоняется. Каждый `existing_manual_evidence_id` должен существовать в реестре и иметь точно тот же документ/хеш/версию/страницу/регион/печатный номер. Для успешного ответа требуется покрытие обоих Evidence входных фактов; одинаковые hits не удваивают покрытие, противоречивые копии дают конфликт.

Поле `hit.text` **не является числовым входом**. Даже неправильное число или инструкция внутри него не изменяют калькуляцию по ранее проверенным Fact. Такой текст не подтверждается заново и не становится источником нового факта. Связка доверяет прежнему реестру и точным метаданным; это не самостоятельная семантическая экспертиза текста и не аутентификация произвольного внешнего JSON. В текущем CLI выдача получается живым локальным `search_index`, проверяющим исходный PDF; загрузки стороннего файла с «готовой выдачей» в CLI нет.

Для финансового/временного отказа калькулятора его причина сохраняется до разрешения поисковых ссылок: результат поиска не может сделать факт доступным в прошлом или исправить несовместимые периоды. При конфликте ID/поиска ответ с вычислением удаляется из конверта, `inputs/sources` пусты; отказ не сопровождается скрытым численным результатом.

## Отказы и технические ошибки

- `missing`: нет значения, кандидат ещё не проверен, неизвестна публикация или нет обоих Evidence в выдаче.
- `conflict`: периоды/единицы/границы расходятся, несколько кандидатов, неправильный порядок ID, противоречивый поисковый фрагмент.
- `unsupported`: другая операция/методика, нулевая или отрицательная база. Текущее нулевое значение допустимо и даёт −100%.
- `error`, exit code **2**: несуществующий ID, одинаковые ID, повреждённая структура/ссылка/хеш/локатор, ошибка файла/индекса, неправильный timestamp/выходной путь. Это не утверждение, что в отчётности нет показателя.

Финансовый отказ возвращается как успешное выполнение инструмента с exit code **0** и явным статусом; численного расчёта нет. Выход `--output` разрешён только под `output/` или `tmp/`, чтобы не перезаписать реестр/код. В конверте нет полного текста PDF или hits, только минимальные факты/локаторы. Полные источники и индекс остаются в исключённой `tmp/`.
