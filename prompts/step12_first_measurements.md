Если ядро всё же потребует исправления, сначала запиши исходный hash/причину/версию; покажи явную разницу и отдели измерение после изменения. Проверка заморозки должна по-прежнему защищать исходный набор/ожидания.

Сначала сохраняй raw structured result, пользовательский текст, минимальный trace, времена/ошибки/usage, затем вычисляй оценку. В run manifest должны быть:

- run_id и действительное время с timezone, case IDs/split/origin/suite, код и хеши данных/версий, соответствие входа frozen reproduction;
- B либо C/LLM либо C/mock/component, реальная adapter metadata, prompt/controller/tool schema hash, параметры/лимиты, model/server digest, search query/top_k и фактическое покрытие Evidence;

Не сохраняй полный PDF/страницы/извлечённый текст/hit bodies, секреты или внутренние рассуждения модели. Штатные минимальные наблюдения/структурированные действия и факты достаточно. Локальный сервер не требует API-платежа, но электричество/стоимость оборудования не измерялись: денежную себестоимость укажи неизвестной, не выдумывай нулевую общую стоимость. Токены бери из фактических `prompt_eval_count/eval_count`, как их возвращает adapter; отсутствующие counters — null/unknown, не оценка по длине строки. Для mock модельных токенов нет.

Для B удобно использовать `run_user_query` и структурированный UserResponse вместо ненадёжного извлечения цифр из CLI-текста. Для C — настоящий `run_agent` с `OllamaAdapter` из конфигурации, как в CLI. Финансовый payload перепроверь `validate_financial_result`. Эта проверка подтверждает договор результата, а не сама по себе способность LLM отвечать на вопросы.

`validate_claim_context` шага 11 — контракт будущего **нормализованного структурированного утверждения**, не готовый извлекатель/счётчик качества. Реализуй узкий явный переход от фактически полученного результата к проверяемым claims. Контекст бери из actual result.inputs/sources/answer/request и trace. **Нельзя дописывать отсутствующие в actual evidence/entity/period/unit/version/mode из gold, чтобы результат прошёл**. Если production-result не содержит достаточного подтверждения, фиксируй неподтверждённость; не достраивай ответ эталоном. Сломанный result или агентная ошибка не имеют финансовых claims по умолчанию.

Для QA03 проверяй все четыре ожидаемых числовых утверждения: прежняя выручка, текущая, разность, процент. Учитывай группу/МСФО/показатель/полные периоды/валюту/масштаб/знак/версию/as_of/точные Evidence и формулу. Правильные15,30 без нужного контекста не дают полный успех. Сравнивай `growth_pct_display` с двухзначным эталоном, не длинную внутреннюю дробь напрямую; не вводи новый допуск после просмотра результатов. Требуемые смысловые предупреждения и маркировку ручного/synthetic происхождения тоже проверь. Не считай все строки renderer независимыми утверждениями и не скрывай существенные неподтверждённые claims вне выбранных четырёх.

Правильный финансовый отказ требует ожидаемый layer/status/reason и отсутствие числового ответа. **call_limit, timeout, error и отсутствие final не равны missing**. Отдельно можно сообщить «не показано неподтверждённое число», но это не числитель корректных отказов. Не меняй QA07 gold под прошлый или новый провал C. Финансовый historical-запрет и сценарный blocked тоже разные уровни. UI clarification не является отказом финансового калькулятора.

## Метрики и проверка подсчёта

Показывай **x/n**, даже если рядом есть процент, и всегда область применимости:

1. Числовая точность B и C на заранее объявленных ответимых поддержанных financial QA: здесь **n=1 (QA03)** на вариант. Тайм-аут/ошибка/неправильный отказ на этой задаче остаются в знаменателе и дают неуспех, а не исключаются. Это один открытый вопрос на двух реальных фактах.
2. Корректные финансовые отказы: **n=2 (QA06/QA07)** на вариант. Указывай причины, ложные отказы на ответимой задаче и отдельные ошибки исполнения. Не объединяй неуспех C top1 с правильным missing B.
3. Подтверждённость существенных утверждений: claim-level confirmed/checked с явным правилом для исходных фактов и производных величин. Для QA03 ожидаются четыре числовых claims, производные требуют входных Evidence и формулы. Отсутствие claims из-за сбоя — «нет claims/не измерено» по этой метрике, **не100%**; успех вопроса и coverage остаются отдельными.
4. Coverage: **3/10 financial QA доступны текущим B/C**; ещё2 только finance API,5 требуют адаптера. UI01 — отдельное1/1 интерфейса. SC01/SC02 — отдельно2 сценария. Reserved-финансовый B/C-знаменатель0 → «не измерено», не «успешно». Не складывай QA/component/scenario в общий процент качества.
5. Поиск отдельно: наличие **обоих нужных Evidence** в первых k результатов для заявленного query, фактический k и источник. По возможности сохрани минимальные IDs/pages/ranks и воспроизводимую coverage-проверку k1/k5, без полного текста. Нужный источник в поиске и правильный финальный ответ — разные успехи. Повтор одного query в разных QA не делает его независимой поисковой задачей.
6. Время: end-to-end по каждому случаю/варианту с ясными границами, cold load и tool overhead; реально собранные счётчики/затраты. По одному прогону нельзя обещать устойчивую медиану/p95/ускорение. Не выдавай прежние времена шага 9 за новые.
7. Компоненты: QA09/10 правильные финансовые missing/conflict без чисел; SC01/02 точный журнал/расходы/итог/сессии и запреты. Отдельно проверь реальный publication_unknown без сделок, если это часть заранее заявленного scenario safety контроля. Это не доходность реального рынка и не качество агента.

Хоть одна метрика должна **повторно вычисляться только из сохранённых raw-результатов и frozen gold**, без модели, сети, нового поиска и production-решения задач. Сделай команду replay/regrade с тем же числителем/знаменателем; покажи её вывод и сохранённое совпадение. Сохраняй все неудачи и not_run. Новые meaningful тесты оценщика должны отвергать правильный scalar при неверных единицах/периоде/документе/Evidence, ошибочный подсчёт call_limit как отказа, подстановку gold в actual и пустой знаменатель как100%. После изменений один подходящий текущий regression run и проверки новых CLI достаточны; новые ошибки требуют адресной проверки.

Не подстраивай prompts/search/лимиты/ожидания/правило после исходов резервных случаев. Любые следующие исследования — отдельная версия и открытое dev-использование. Нельзя утверждать превосходство C, качество всей системы или рыночный эффект по этим единичным задачам.
