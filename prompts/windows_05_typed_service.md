# WIN-05 · Общий сервис и типизированный протокол финансового ассистента

Продолжай Windows-план «Проектной практики» в `financial-report-agent`. После
сверки WIN-04 создай отдельную ветку `codex/` и рабочую копию. Прочитай AGENTS.md,
STATUS.md, рабочую часть handoff, `docs/windows/roadmap.json`,
`docs/windows/application_paths.md` и `docs/github_collaboration.md`.

1. Выдели один версионированный `ApplicationService` для зафиксированного расчёта
   учебной маржи. Передавай выбранный `WorkspaceContext` при запуске из доверенного
   контейнера. В запросе разреши только закрытые поля версии, `run_id`, идентичности
   контекста, команды и аргументов. Логический ID ресурса допустим. Файловые пути,
   строка запуска, произвольные команды, SQL и opaque аргументы недопустимы.
2. Введи ограниченный UTF-8 JSONL обмен через отдельный фиксированный процесс.
   Выбери и задокументируй пределы байтов, одну завершающую запись, корреляцию всех
   полей, завершение процесса и отдельный сток ограниченной диагностики. Откажи
   при дублях полей, лишних типах, неверном ID, устаревшем контексте, лишнем кадре
   или аварийном завершении даже после похожего на успех ответа.
3. Подключи новый CLI и нативного потребителя к одному сервису. Если оконный
   потребитель ещё не прошёл наблюдаемый тест, укажи фактический объём проверки.
   Повтори `15.00` на собственном PDF в двух vault с исходным SHA и рамкой.
   Сохраняй подтверждённую квитанцию один раз. При техническом отказе результат
   пуст. Повторный ID не перезаписывает прежнюю квитанцию.
4. Проверь несогласованную/избыточную схему, типы, context mismatch, параллельный
   duplicate ID, некорректный UTF-8, обрезанный/превышающий лимит ответ, неверную
   корреляцию, stderr и краш. Legacy WPF/runtime, модели, данные эмитентов и KP3 RC
   не меняй. Supervisor, SQLite и расширенная оболочка идут отдельными этапами.
5. Сохрани статус, проверяемые квитанции, следующий промт и GitHub PR. Продолжай
   Windows-план по `depends_on` без паузы между готовыми этапами.
